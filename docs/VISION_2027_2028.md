# CodeContext — 2027–2028 Product Vision

## Why this document exists

CodeContext has grown from a repository analyzer into a deterministic engineering-intelligence foundation. This document defines the next product direction: solve problems that become harder, not easier, as AI makes code generation faster.

The strategic premise is simple:

> **AI can generate code. CodeContext should make engineering changes provable, explainable, governable, and safe.**

## The problem AI does not solve by itself

Modern coding agents can generate and modify code quickly, but speed does not automatically answer:

- What does this change actually affect across a large system?
- Which architectural boundaries will it cross?
- What hidden knowledge or ownership does the change depend on?
- Which contracts, migrations, policies, and operational assumptions can break?
- Can we prove that the generated change was safe for this exact repository state?
- What changed in the system's architecture over six months?
- Which dependencies or services are becoming single points of failure?
- What should an agent be forbidden from doing, and can that policy be enforced mechanically?

CodeContext should own this evidence and verification layer.

## Product thesis

Build an **Engineering Evidence Platform** with five layers:

```text
Repository + Git + CI + Runtime signals
                ↓
        Unified Engineering Model
                ↓
   Deterministic Evidence + History
                ↓
 Governance / Simulation / Verification
                ↓
      AI reasoning and agents
```

AI remains an optional reasoning layer. The evidence system remains useful without AI.

## 2027–2028 flagship capabilities

### 1. Engineering Digital Twin

Maintain a versioned model of the repository and its engineering relationships:

- files, symbols, packages, modules, services;
- dependency and call relationships;
- owners and knowledge concentration;
- APIs and contracts;
- architecture rules;
- Git history and change patterns;
- CI/test evidence;
- migrations and infrastructure relationships;
- snapshots over time.

The key differentiator is **time**: answer how the system changed, not only how it looks today.

### 2. Change Proof / Impact Proof

For every significant change, produce a machine-readable proof package:

```text
Change
  → affected components
  → dependency blast radius
  → architecture boundaries crossed
  → ownership impact
  → security/policy impact
  → test evidence
  → CI evidence
  → unresolved uncertainty
```

This is more useful than a generic AI review because every claim can be traced to evidence.

### 3. Counterfactual Change Simulator

Before merging a risky change, estimate multiple scenarios:

- what breaks if dependency X is unavailable;
- what becomes unreachable after a boundary change;
- what services are affected by a schema/API migration;
- what happens if a high-centrality component changes;
- which tests are insufficient for the affected graph.

Start with deterministic graph simulation. Add AI explanations later.

### 4. Architecture Constitution

Allow teams to declare architecture as executable policy:

```yaml
rules:
  - id: payments-no-ui-dependency
    from: payments
    cannotDependOn: ui

  - id: api-must-not-access-db
    from: api
    cannotDependOn: persistence
```

CodeContext evaluates these rules continuously and produces evidence when they drift.

### 5. Agent Firewall / Agent Governance

Create a policy boundary for coding agents:

- allowed repositories;
- allowed directories;
- protected files;
- prohibited operations;
- maximum change size;
- required tests;
- required reviewers;
- required architecture checks;
- secret/data boundaries;
- mandatory CI gates.

An agent should receive a mechanical **allow / deny / require-review** decision before an autonomous action.

### 6. Change Risk Budget

Replace a single risk score with an explainable risk budget:

- dependency risk;
- architecture risk;
- security risk;
- ownership risk;
- migration risk;
- test-confidence risk;
- change-size risk;
- historical instability.

Teams can configure policies such as: "high migration risk requires explicit approval" rather than relying on one opaque number.

### 7. Knowledge Continuity Graph

Detect organizational knowledge loss:

- components with one meaningful contributor;
- abandoned critical modules;
- ownership gaps;
- reviewers who are no longer active;
- undocumented operational knowledge;
- changes repeatedly requiring the same expert.

Generate onboarding and succession plans from evidence rather than surveys alone.

### 8. AI Change Provenance

Track an auditable chain:

```text
Requirement
 → AI plan
 → evidence used
 → generated patch
 → human edits
 → CI runs
 → review decisions
 → merged commit
```

This creates a provenance record for AI-assisted engineering.

### 9. Migration Guardian

Treat database/API/framework migrations as first-class changes.

Detect:

- old/new contract overlap;
- consumers not yet migrated;
- incompatible schema changes;
- rollout ordering requirements;
- rollback hazards;
- missing compatibility tests.

This targets a class of failures that code generation alone cannot reliably eliminate.

### 10. Production-to-Code Feedback Loop

When runtime telemetry becomes available, correlate:

```text
production symptom
      ↓
service / endpoint
      ↓
code ownership
      ↓
dependency graph
      ↓
recent changes
      ↓
likely change surface
```

Keep runtime connectors optional and permissioned; do not require production access for local analysis.

## Open-source growth strategy

CodeContext should be useful as a CLI before it becomes a platform.

### Developer wedge

```text
codecontext analyze .
codecontext pr-intelligence .
codecontext repo-qa "why is X risky?"
codecontext plan "change payment validation"
```

### CI wedge

Produce:

- JSON;
- SARIF;
- PR comments;
- check-run summaries;
- architecture-policy failures.

### Enterprise wedge

Add optional services for:

- repository registry;
- historical snapshots;
- organization architecture maps;
- governance policies;
- identity/ownership integrations;
- audit and provenance.

## Technical principles

1. Deterministic evidence before AI reasoning.
2. Version every important evidence schema.
3. Make results reproducible for the same repository snapshot and configuration.
4. Never treat model confidence as repository truth.
5. Make uncertainty first-class.
6. Prefer explainable signals over opaque aggregate scores.
7. Keep local-first operation viable.
8. Make CI the reference execution environment.
9. Keep security boundaries explicit before enabling agentic behavior.
10. Design for polyglot repositories even if the initial implementation is JVM-focused.

## Success measures

Measure engineering outcomes rather than AI token volume:

- reduced escaped architecture violations;
- reduced time to understand unfamiliar systems;
- reduced review/rework caused by missed dependencies;
- reduced migration incidents;
- faster incident-to-change-surface identification;
- fewer critical components without ownership;
- higher percentage of AI-generated changes with verified evidence;
- reproducibility of analysis across CI runs.

## Non-goals

CodeContext should not become another generic coding chatbot, code autocomplete product, or opaque AI reviewer. Its durable advantage should be the **engineering evidence graph, temporal history, verification system, and governance layer** that other AI systems can consume.
